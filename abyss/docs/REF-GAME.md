# Разбор референса: com.entropy.global (xapk v628)

Технический и дизайнерский разбор чужого мобильного релиза для поиска идей для Project Abyss.
**Ничего из кода, графики, звука, текстов и уровней этой игры не копируется и не переносится** —
ниже только устройство систем (своими словами) и то, что из этого устройства стоит взять как приём.

Источник: `com.entropy.global_628.xapk` (2.3 ГиБ), распакован в `unpacked/` рядом с файлом
(вне git, по месту хранения xapk — не в этом репозитории).

---

## 1. Движок, структура, форматы, размеры

### Контейнер

`.xapk` — обычный ZIP с набором split-APK от Android App Bundle (так публикуют в сторонних
магазинах/лоадерах, Google Play доставляет то же самое через Play Asset Delivery). Внутри 83 файла:

| Группа | Файлы | Вес | Назначение |
|---|---|---|---|
| Основной APK | `com.entropy.global-628.apk` | 53 МБ | код (Kotlin/Java), манифест, Android-ресурсы, веб-ресурсы паблишерских SDK |
| Асс­ет-пак | `asset_pack-628.apk` | 2.4 ГБ | **весь игровой контент** (см. ниже) — именно он играет роль классического `.obb`, но физически это такой же APK/ZIP |
| ABI-сплиты | `config.arm64_v8a-628.apk`, `config.armeabi_v7a-628.apk` | 260 МБ + 222 МБ | нативные библиотеки под 64- и 32-бит ARM |
| Density-сплиты | `config.hdpi/mdpi/xhdpi/xxhdpi/xxxhdpi` | по 60–100 КБ | иконка приложения под разные плотности экрана |
| Language-сплиты | ~75 файлов `config.<locale>-628.apk` | по 25–70 КБ | **только системные Android-строки** (разрешения, системные диалоги) — игровой текст и локализация живут отдельно, см. §1.4 |

Отдельного `.obb`-файла в пакете нет — это не классическая Android-схема «APK + OBB», а более
новая Play Asset Delivery: весь тяжёлый контент — ещё один «APK», который устанавливается как
дополнительный пакет и просто читается как файл с ресурсами.

### Движок

- **Unity 2022.3.27f1**, скриптовый backend — **IL2CPP** (C# компилируется в C++ и собирается в
  `libil2cpp.so`, 225 МБ на arm64; рядом `global-metadata.dat`, 49 МБ — метаданные типов для IL2CPP).
  Рантайм движка — `libunity.so` (21 МБ).
- **Поверх C#/IL2CPP — слой бизнес-логики на Lua** через `xLua` (`libxlua.so`, ~3 МБ) и генератор
  `Libs/flatbuffers` среди Lua-модулей. Это типичная архитектура крупных мобильных SLG: ядро
  (рендер, физика, сеть) — на C#/IL2CPP, а игровые правила, баланс, большая часть UI-логики —
  на Lua, чтобы «горячо» править баланс и фиксить баги без пересборки и прохождения ревью в сторе.
- **UI** — смесь старого **NGUI** (отдельная папка ресурсов `ngui_atlas`) и современных Unity UI
  префабов; часть экранов, судя по путям (`ad-viewer`, `kg-sdk-webview`, `kg_local_html`), — это
  встроенные веб-вью (HTML/JS), а не Unity-сцены — обычно так делают баннеры акций и некоторые
  соглашения/формы.
- **Аудио** — Wwise (`libAkSoundEngine.so`) + Dolby Audio360 — профессиональный звуковой стек,
  рассчитанный на большое количество озвученных реплик и адаптивную музыку.
- **Видео** — AVPro (`libAVProLocal.so`) для встроенных видеороликов/рекламы.
- **2D-анимация персонажей** — **Spine** (папка `SpineAssets`, десятки файлов
  `<имя>_resource_spine_proxy.ab`) — скелетная анимация для портретов/аватаров героев и части VFX.
- **Сервисы**: Firebase (Analytics, Auth, Crashlytics, Installations, Cloud Messaging),
  Google Play Games (`libgpg.so`), Google Play Billing 8.3.0, плюс собственный SDK
  публикующей платформы (префиксы `fp_`, `kg_`, `funplus-` в именах ассетов и папок — аккаунт,
  веб-вью, CMS для баннеров, подсказки) — профиль стека типичен для крупного паблишера мобильных
  стратегий (в духе FunPlus и похожих студий).

### Форматы ресурсов

Внутри ассет-пака — **Unity AssetBundle** (`.ab`, формат `UnityFS`, подтверждён заголовком файла:
сигнатура `UnityFS` + версия движка `2022.3.27f1`; блоки сжаты, судя по флагам — LZ4). Бандлы лежат
в двух хранилищах:

1. **Человекочитаемый кэш** `assets/build/cache/<Категория>/<Подкатегория>/*.ab` — именно он дал
   основную информацию для раздела 2 ниже: имена папок и файлов прямо называют игровые системы.
2. **Машинный кэш** `assets/bin/Data/<32-символьный hex-хеш>` — около 18 500 файлов без расширений,
   имя — хеш содержимого (классический паттерн Addressables/Play Asset Delivery: ссылки на ассет
   уходят через каталог, а не через путь). Рядом — служебные файлы движка верхнего уровня:
   `globalgamemanagers`, `sharedassets0.assets`, `level0`, `unity default resources`,
   `ScriptingAssemblies.json`, `boot.config`.

**Локализация текста — не JSON, хотя и названа `*.json.bin`.** Отдельный архив
`assets/build/Language.zip` (14.6 МБ) содержит по файлу на язык (`InGameLanguage/language_en.json.bin`
и т.п., плюс отдельный набор `LoadingLanguage/*` для экрана загрузки). Формат — свой бинарный:
заголовок (версия, количество записей — около 43 700 строк на английский), дальше последовательность
записей «длина-префиксная строка-ключ + 4-байтная ссылка на пул переводов». То есть ключи вынесены
отдельно от переводов — вероятно, из соображений компактности и чтобы перевод не вытаскивался простым
просмотром строк в файле. Сами ключи (например, идентификаторы вида «тип_подсистема_номер») уже
раскрывают структуру контента без необходимости доставать сами переводы — на них и построен разбор
механик ниже.

## 2. Механики и системы

Жанр — мобильная «SLG» (4X-стратегия с осадой и альянсами) в духе Rise of Kingdoms / State of Survival,
с постапокалиптическим сеттингом на технике: вместо чисто средневековых войск — вездеходы/броневики
с заменяемыми деталями (упоминаются детали вроде «zeus», «roller», «fallout»), ракетные установки
(`MissileSystem`) и модификация техники (`VehicleDisplay`, `VehicleModification`). Ниже — системы,
которые видны по категориям ресурсов и по осмысленным идентификаторам ключей локализации (не по
самим переводам — переводы не вытаскивались).

**База / город.** Строительство на сетке с 3D-видом города (`City3D`), стены как отдельная сущность
обороны (`CityWall`), типовые здания с уровнями (лесопилка, «материальная фабрика», склад,
тренировочный лагерь для войск). Несколько ландшафтных «тем» карты (замороженная зона, пустыня,
побережье, вода) — похоже на разные игровые миры/сервера с разным оформлением, а не просто биомы
одной карты.

**Карта королевства.** Общая карта (`Kingdom`) с отдельными наборами данных на каждый
регион/сервер (`KingdomData/Frozen`, `.../Desert_1`, `.../Eastcoast` и т.д. — то есть при запуске
нового «сезона/сервера» переиспользуется тот же движок с новым набором данных). На карте —
территориальный контроль (`Territory`), укреплённые точки/бункеры с наградами, добыча ресурсов
точками на карте (упоминание «шахта королевства»).

**Экономика.** Явно выделенные виды ресурса (еда, древесина/«lumber», руда — судя по ключам вида
`item_ore_small…`), рынок между игроками с комиссией (`marketplace`, упоминание налога и статусов
отправки/обмена), «фрахт»/конвои (`Freight`) как отдельная сущность передачи ресурсов, общий склад
альянса с донатом в фонд (`alliance_warehouse`, `alliance_resource_donate`).

**Прокачка.** Дерево технологий минимум по двум веткам — «экономика» (скорость добычи/исследований)
и «бой» (открытие юнитов, их характеристик); у узлов есть сохранённые позиции на экране дерева
(`bigTechPos`) — то есть это визуальный граф, а не список. Усиление оружия через «вес усиления» и
фрагменты, экипировочные «чипы» с процентными бонусами (в т.ч. шанс крита), аксессуары, таланты
героев (пассивные и активные, с «аффиксами» — модификаторами эффекта). Отдельная прогрессия
достижений (`achievement`).

**Герои («генералы»).** Командиры со своими навыками/талантами, которые добываются через фрагменты
(гача-механика), экипировкой, скинами, короткими голосовыми репликами и мини-историями (сюжетные
вставки на конкретного героя). Войска типизированы по родам (пехота/«броня»/дальний бой — встречаются
отдельные описания для «ranged_t1», «ranged_t3» и т.п.), перед боем собираются в построение
(`Formation`/`Lineup`, отдельно хранятся позиции построения — `TroopComposeLinePos`).

**Бой.** Отдельный экран боя (`Fight`) с всплывающими числами урона. После каждого столкновения —
подробный **отчёт о бое** (`BattleReport`): построение сторон, потери, баффы, трофеи/экипировка —
развёрнутый пост-бой экран, а не просто «вы победили». Режимы: PvE-кампания по главам с диалогами и
«тактикой» (вероятно, бой с особыми условиями), подземелья (в т.ч. совместные PvE-«дженджоны» на
несколько игроков), арена 1×1, турнирная арена на выбывание с «сезонами чести», мировой босс,
периодические «дни охоты» (PvE и PvP варианты одного события), охота за наградой за конкретного
врага (`BountyHunter`).

**Альянсы.** Полноценная гильдейская подсистема: информация и лог вступления/повышений, декреты
(правила/объявления от лидеров), политика ускорения строек, которую назначают администраторы альянса,
альянсовый технологический вклад, альянсовый босс, приглашение вернувшихся игроков. Крупномасштабные
межальянсовые режимы — «альянс против альянса» со системой очков за точки на карте, региональные
гонки, отдельный «военный фронт»/«военная зона» как режим большой карты.

**Социальное.** Чат с эмодзи и ограничением длины имени комнаты, почта (в том числе системные письма
о модерации — баны и т.п.), настраиваемая «визитка» профиля игрока, настройки.

**Сезон/сервер как мета-слой.** Таймеры начала/окончания сезона, межсерверные («кросс-сезонные»)
события, перенос персонажа между серверами с ограничением свободных слотов в зоне назначения.

**Монетизация.** Отдельный центр покупок с баннерами лимитированных предложений, боевой пропуск
(покупка/прогресс), лутбоксы разного типа (в т.ч. «сундук с повышением уровня»), прямая покупка
ресурса за валюту.

**Обучение.** Многоступенчатый туториал, который хранится **версионированно по «мирам»** —
на каждый новый сервер/сезон (`ClientConfig/base`, `.../s1.b`, `.../s1.c`, …) лежит свой набор
данных обучения и карты стартовой застройки, то есть обучающий сценарий переиспользуется как шаблон
с заменяемыми данными, а не переписывается кодом под каждый новый мир.

## 3. Интерфейс: экраны и их назначение

Ниже — инвентарь экранов по именам папок/префабов (сами префабы и картинки не извлекались и не
переносились — только список того, что за экраны существуют и, судя по названиям, за что отвечают).

- **Loading** — экран загрузки (у него собственный, отдельный от игрового, набор переводов).
- **Huds/HudNew** — основной HUD поверх города: круговое меню действий, контейнер-обёртка HUD.
- **Kingdom / City** — переключение между видом города и картой королевства.
- **General / HeroEquipment / Illustrated** — экран героев-«генералов», их снаряжения и, судя по
  названию, иллюстрированной галереи/бестиария (коллекционный лог по открытым героям/существам).
- **Unit / Military / Formation / Lineup** — состав войск и построение отряда перед боем.
- **Weapon / VehicleDisplay / VehicleModification / Chip** — техника, её детали и чиповое усиление.
- **Shop / IAP / IAPCenter** — магазин ресурсов и отдельный центр покупок с акциями.
- **Recruit** — набор героев (баннеры гачи).
- **Alliance / AllianceKof / Decrees / Territory** — гильдия, её «военный» режим, правила, карта
  территорий.
- **Arena / PVP / WarZone / BattleReport** — ПвП-режимы и отчёты по боям.
- **Dungeon / PVE / Campaign** — подземелья и сюжетная кампания.
- **ActivityCenter** — десятки отдельных попапов под конкретные акции и события (сезонные ивенты,
  розыгрыши, тематические предложения) — это не один универсальный экран, а библиотека готовых
  шаблонов попапов под каждое событие.
- **Mail** — почта/уведомления.
- **ChatNew / ChatAssistant / Emoji** — чат и его вспомогательные экраны.
- **Quest** — список заданий.
- **ChangeServer** — перенос персонажа на другой сервер.
- **Killbroadcast** — всплывающие уведомления о значимых событиях на сервере (кто-то кого-то
  победил/захватил точку и т.п.).
- **PlayerDiy / Ornament** — кастомизация профиля/визитки.
- **GM** — служебное/отладочное меню, не предназначено для обычных игроков (осталось в сборке).

Иконки и кнопки сгруппированы в текстурных атласах по тем же категориям (отдельные наборы под
`Button`, под ресурсные иконки, под иконки конкретных активностей, под чат-эмодзи) — то есть у
каждой крупной системы свой изолированный набор графики, без общего «мусорного» атласа на всё.

## 4. Что стоит взять в Project Abyss (приёмы, не контент)

Project Abyss — другой жанр (сюжетный sci-fi survival horror, отряд героя + подводная база-конструктор
в духе Emperor/Kenshi, без PvP и без серверной мультиплеерной экономики — см.
[README](../README.md), [BASE-BUILDER.md](BASE-BUILDER.md)). Поэтому большая часть многопользовательских
систем referенса (альянсы, PvP-арены, сезон-серверы, гача за деньги, маркетплейс с налогом) **не
подходит по жанру и намеренно не рассматривается**. Ниже — только то, что переносится как приём
устройства системы, с привязкой к уже существующим файлам Abyss:

1. **Явный индикатор причины простоя станка.** В референсе у станка без сырья или без энергии
   отдельно отмечается, что рабочий ушёл именно по этой причине. В `base-sim.js` сейчас простой
   станка от нехватки энергии уже помечается («нет энергии»), но стоит унифицировать: один общий
   «значок причины простоя» (нет сырья / нет энергии / никто не назначен) над любым устройством,
   а не только над станком без тока — это дешёвый UI-приём, сильно снижающий фрустрацию игрока,
   который не понимает, почему цепочка производства встала.

2. **Визуальный граф дерева исследований вместо списка.** У референса позиции узлов технологий
   хранятся отдельно от самих технологий (именно под раскладку графа). `AB.BASE_TECH` в
   `js/data/base.js` уже поделён на 4 ветки — стоит на этапе интерфейса (§5 плана в
   [BASE-BUILDER.md](BASE-BUILDER.md)) сразу закладывать координаты узлов в данных, а не только
   связи branch/`tech`-требование, чтобы дерево рисовалось как граф, а не как раскрывающийся список.

3. **Пост-бой отчёт как отдельный маленький экран.** После каждого серьёзного столкновения у
   референса — сводка: кто с кем дрался, потери, что выпало. Для Abyss после «Гнезда»/арен и боссов
   стоит собирать аналогичную компактную сводку (ранения, трофеи, полученный опыт) вместо того, чтобы
   это растворялось в общем журнале сообщений — так игрок сразу видит цену победы.

4. **Параметризованные шаблоны квестов.** У референса один код квеста обслуживает много вариантов
   через параметры («собери N ресурса такого-то типа», «постройте здание такого-то типа до уровня N»)
   — вместо отдельного квеста на каждую комбинацию. У Abyss задания пока штучные (`QUEST-001` и т.д.);
   когда появятся повторяемые побочные задания, стоит сразу делать их через 1–2 общих шаблона с
   параметрами (тип ресурса/цели, количество), а не плодить `QUEST-00N` под каждую комбинацию.

5. **Модификаторы снаряжения как отдельный слой над базовым предметом.** «Чипы» референса добавляют
   процентные бонусы к оружию/броне без изменения самого предмета. Для EQUIPMENT SYSTEM Abyss это
   выглядит как необязательный слот-модификатор у `EQUIP-*` (например, найденная деталь даёт +X% к
   какому-то параметру), который можно вынести отдельным простым объектом, не трогая базовые данные
   предмета — расширяемо и легко обратимо, если баланс не понравится.

6. **Выбор построения отряда как отдельный экран, а не только порядок следования.** Сейчас в
   PARTY SYSTEM Abyss расстановка — это просто «кто ведущий». Явный мини-экран «кто куда» перед
   сложным испытанием (кто принимает удар первым, кто бьёт издали) — дешёвая механика, которая
   добавляет тактики без изменения боевого кода, только интерфейс поверх существующих ролей
   (ближний/дальний бой у спутников).

7. **Единая «служба красных точек» вместо точечных проверок на каждом экране.** В референсе
   среди Lua-библиотек есть отдельный модуль именно для индикаторов непрочитанного/невыполненного
   («RedDot»), а не разбросанные по экранам проверки. У Abyss уже есть похожая идея для находок
   (непрочитанные мерцают в LOG SYSTEM) — стоит обобщить её в один небольшой сервис-реестр
   «что подсвечивать», которым будут пользоваться и журнал находок, и инвентарь, и будущие системы
   (например, готовая технология в дереве исследований), вместо копирования одной и той же логики
   мерцания в разных местах.

8. **Валидация подхода с реестром ID.** Косвенное наблюдение: у референса (как и у большинства
   крупных игр такого масштаба) все данные построены вокруг стабильных строковых идентификаторов,
   а переводы и графика подвязаны к этим идентификаторам, а не наоборот. Это ровно та архитектура,
   которую Abyss уже выбрал через `AB.ID`/`AB.Bus` — повод не менять подход, когда база данных
   вырастет (герои, предметы, технологии), а не повод что-то копировать.

**Сознательно не переносится:** PvP между игроками, альянсы/гильдии, гача за реальные деньги,
сезон-сервера и межсерверные переносы, маркетплейс с комиссией, баннерная монетизация — всё это
обслуживает соревновательную мультиплеерную SLG-экономику, которой в Project Abyss нет и не
планируется.
